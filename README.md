# Loci (Marketplace 2.0 prototype)

A clickable prototype of a centralized procurement marketplace: any city, county or school district searches state and cooperative contracts in one place, sees which ones it may use, and buys. Searching it is free. Two products are sold on top of it: a **city marketplace** for an agency (a white-labeled Loci with its own contracts and rules) and a **storefront** for a supplier (its own page listing its catalog). The supplier side and Sovra's revenue mechanics are visible on screen too. It's built for leadership demos, not production: seeded data, no real integrations, and one live city marketplace (the fictional City of Riverbend).

## The marketplace, city marketplaces and storefronts

Three names, kept distinct everywhere in the app:

| Name | What it is | Who pays | Where |
| --- | --- | --- | --- |
| **Loci** | The shared marketplace anyone can search | Free to search | `/` |
| **City marketplace** | A white-labeled Loci for one city, county or district: its contracts, rules, approvals and brand, for its own staff | The agency, by subscription (option 1) | `/marketplaces`, `/marketplaces/riverbend` |
| **Storefront** | A supplier's own page: its catalog, the contracts it sells through, certifications and reviews | The supplier: a basic page is free, the featured storefront comes with Edge Position (option 6) | `/storefronts`, `/storefronts/[supplier]` |
| **Program page** | A purchasing program's own page (NJSTART, Sourcewell, …): what it covers, who holds its contracts, the prices on file and how a local buys through it | Built from the catalog for every program; nobody claims it | `/programs`, `/programs/[program]` |

A supplier can also pay to list its piggybackable contracts in more cities' marketplaces (option 4, Supplier → City marketplaces). Supplier names on result cards and product pages link to their storefronts.

The home page (`/`) is the marketplace. It asks one question, "What are you looking to buy?", and searches every contract in Loci without needing an agency. Setting an agency (account menu → **Your agency**, or **Set your agency** on any results page) hides the contracts that agency can't use; leaving it blank shows who each contract is open to.

**The front door.** A request for a product doesn't jump to a results page. The hero folds into a request bar with four steps (Describe, Narrow, Route, Plan), and the product dive opens underneath (`components/FrontDoor.tsx`). Loci first asks who is buying, unless an agency is already set, because the agency decides which contracts are open. Next it asks how many, unless the request already says (the "40" in "40 folding tables" is read and shown as a chip). Then it asks the dive's own questions about the product. Every card shows the order's total and how it would be bought: a P-card under the quick-buy limit, or a purchase order at or over it. The quick-buy limit is the agency's own when the buyer is the home agency, and a typical one otherwise. **Choose this one** opens the product's route in place. For a Loci listing, **Plan this purchase** opens the results page with the item already confirmed (`confirmPick`). For a co-op or state product, the buyer can order on the program's site, open the contract or start the purchase file. Under the shortlist, **None of these fit?** offers three ways out, least work first: a quote under a contract the agency can already use, quotes from a few suppliers, or a solicitation. The recommended one follows from the estimated total, drawn against the quick-buy limit on a meter (`offRamp` in `lib/front-door.ts`). The total is quantity times the typical prices on the shortlist, the middle 80% once there are more than five, so a stray match doesn't set it. The buyer state's rules on quotes and formal bids are quoted beside the paths with their sources. They are not turned into numbers. The panel opens above the shortlist when one product or none is left, or nothing has a price. The address keeps the request, the answers and the quantity (`/?q=…&f=…&n=…`), so a refresh or a shared link returns to the same shortlist and Back returns to the hero. **See full results** is always one click away. Requests for software, services and construction (`requestKind`), and any request with no product in the catalog, go straight to the results page and its contract sections, as before. A request record is created only when the buyer leaves for the results page, a contract route or a solicitation.

**For cities** (`/marketplaces`) lists the city marketplaces. Riverbend's (`/marketplaces/riverbend`) is live: searching there searches as Riverbend, with its own contracts, local-vendor preference, $10K quick-buy limit, renewals coming due and reorders. The others on the list are shown as available to sell. **Storefronts** (`/storefronts`) lists every supplier; each storefront has the supplier's contracts, a searchable catalog and agency reviews.

## Running it

`HANDOFF.md` says where the work stands and what's next; `CLAUDE.md` has the working notes for coding agents (commands, data pipeline, data rules).

```bash
npm install
npm run dev        # http://localhost:3000
```

Everything works offline. To have Claude (`claude-sonnet-5-5`) parse requests and structure uploaded contracts, copy `.env.example` to `.env` and set `ANTHROPIC_API_KEY`. Without a key, a keyword matcher and a regex-and-table contract parser take over, and the header shows an "Offline parsing" tag. Any API failure falls back the same way.

State is kept in memory while the app runs and, when `DATABASE_URL` is set, saved to Postgres so a restart or redeploy doesn't lose it (see **Accounts and saved data** below). Without `DATABASE_URL`, which is how local runs and the rehearsal work, it stays in memory only. The home page has a **Select your agency** control under the search box.

## Accounts and saved data

**What needs an account.** Anyone can search, set their agency, and use every public feature that draws on the AI, with no account: the buying plan and its questions, paperwork drafts (unsigned without an account), the product dive, the quote check, Ask a contract and the contract brief. Anyone can also fill a cart, like any online shop: it is kept for that browser until checking out or handing it off, which asks them to sign in or create an account and then carries on, with the cart moved to the account. An account is needed for anything that keeps a record for a person or an agency: checkout and orders, quote requests, asking purchasing about a co-op, solicitations, the purchasing pages, the supplier side and uploads. The check is on the server: `/api/act` lists the open actions and answers 401 for the rest, and the upload routes do the same (`withSession` in `lib/session.ts`). Two actions change the demo for everyone, **Reset demo** and approving a supplier's claim, and need an admin (`ADMIN` in `app/api/act/route.ts`, `lib/admin.ts`). On a server that saves its state (`DATABASE_URL` set) an admin is a confirmed, unsuspended account that is either listed in `AGORA_ADMIN_EMAILS` (comma-separated: the root admins) or was made an admin by another admin at `/admin`; everyone else gets a 403 and doesn't see the buttons. On a server that saves nothing, such as a local build or the rehearsal, any signed-in account counts, since nothing it does outlives the process. In the browser, a step that needs an account opens the sign-in dialog and then carries on with what the person was doing; account-only pages show a sign-in panel instead (`components/Account.tsx`).

**Accounts.** Email and password (`lib/auth.ts`, `/api/auth`). Passwords are stored as salted scrypt hashes and session tokens as SHA-256 hashes, so neither can be read back. The session is an HttpOnly cookie that lasts 30 days. Five wrong passwords for one email pause sign-in for ten minutes. An account has a name, an email, what the person does (buyer, purchasing or supplier, which sets the side of Loci they start on) and their agency. The account's role doesn't restrict what a signed-in person can open: the **View the demo as** switcher still works for everyone.

**Email.** With `RESEND_API_KEY` set, Loci sends mail through Resend from `EMAIL_FROM` (`lib/email.ts`, `lib/notify.ts`). Without the key nothing is sent and accounts still work.

- **Confirming an address.** Signing up sends a link that works once and lasts three days (`/verify`). An unconfirmed account works as normal; the account menu offers to send the link again.
- **Resetting a password.** **Forgot your password?** in the sign-in dialog sends a link that works once and lasts an hour (`/reset`). The form answers the same way whether or not the email has an account. Choosing a new password signs the account out everywhere else and confirms the address.
- **Approval notices.** Purchasing staff at an agency are told when a cart or a purchase order is waiting for approval and when a requester asks about a co-op. The requester is told when their cart is approved or sent back and when their purchase order is approved. Purchasing staff are the accounts that chose "I work in purchasing" and whose agency matches.
- **Limits.** Notices go only to confirmed addresses. An address gets at most three link emails an hour. Link tokens are stored only as hashes. Sending never holds up the action that triggered it; a failure is logged.

**Site admin** (`/admin`, linked from the footer for everyone and from the account menu for admins; a visitor who isn't an admin is told the page is for admins). Four tabs, all served by `/api/admin`, which answers only admins:

- **Overview.** Account counts (confirmed, seen and new this week, admins, suspended), which services this server has (saved state, AI, email, root admins), the shared demo's activity with **Reset the demo**, and the document store's progress. The store's counts are read once per visit and only on this tab (`?view=docs`), because their queries share the database's five connections with the background ingest.
- **People.** Every account, newest first, searchable by name, email or agency, with its role, agency, status and when it was last seen (written at most every five minutes). An admin can change a role, confirm an address or send a confirmation link, send a password-reset link, sign the account out everywhere, make or remove an admin, suspend or restore it, and delete it (typing its email to confirm). A suspended account can't sign in and its sessions stop working at once. Admins must have a confirmed address.
- **Supplier claims.** Claims waiting for review, oldest first, with **Approve** and **Reject**. Rejecting returns the storefront to unclaimed.
- **Activity.** The 25 latest admin actions with who made them, from `/admin` and from the reset and approve buttons elsewhere (`lib/admin-log.ts`, the `admin_log` table).

Two rules keep the site from losing its admins: nobody can remove admin from, suspend or delete their own account, and root admins can't be changed from the page at all (take them off `AGORA_ADMIN_EMAILS` first).

**Who sees what.** Three things come from the visitor's browser as cookies and are bound to each request: their agency, their account, and an id for the browser. A person's agency is theirs alone; with an account it is saved and follows them to another browser. Searches belong to whoever made them, and searches made before signing in move to the account. Carts and orders are still kept per agency, so two people at the same agency share them. The storefront a supplier view acts as is kept per account (or per browser) on the server, so one person switching storefronts doesn't switch anyone else's.

**What the browser receives.** `/api/state` sends the store, cut to what the visitor's agency may see (`app/api/state/route.ts`). Other agencies' contract registers, carts, orders, invites (which carry an email address), quote requests, RFP handoffs and referrals stay on the server. A visitor who hasn't picked an agency is in the demo agency, Riverbend, which is also where seed records without an agency belong. Outbound clicks and search impressions aren't sent at all: the ledger's co-op traffic panel gets counts per co-op and the 20 latest clicks, with another agency's name shown as "Another agency". A supplier claimant's email is shown only to the claimant and to admins. The revenue ledger is still sent whole: it is the demo's business-model panel, and its entries name suppliers and order numbers but no people.

**Saved data.** The store is still the in-memory `Db` every action changes. With `DATABASE_URL` set, `lib/persist.ts` saves the difference between that `Db` and a fresh seed after each change (new and changed records, removed ids and their order, one row per collection in `app_state`) and applies it on top of the seed at start. A change to the seed therefore still reaches the site, except where someone has since edited the same record. Users and sessions have their own tables (`lib/pg.ts`). **Reset demo** needs an admin and clears the saved state for everyone; it leaves accounts alone.

## Co-op contracts link out

Loci doesn't sell through a co-op's contracts. A result on a co-op contract shows **Buy on NASPO ↗** (or Sourcewell, and so on), which opens that contract's own page through a tracked redirect, `/go/[contract]`. Each click is logged with the agency, contract, co-op and request, so Sovra can show every co-op the traffic it sends. This follows the partnerships plan: send traffic first, show co-ops the lift, and only then talk about a share. It also keeps Loci from sitting between a co-op and its members as a reseller would.

A co-op that has agreed can let its members buy inside Loci. Each co-op (`lib/coops.ts`) carries a `buy_in_agora` setting, off by default. In the seed, NASPO ValuePoint and Sourcewell are off because they're real co-ops with no agreement. The fictional WSPC is on, so demo step 1's National Furniture listing can still be bought in Loci. Checkout and quote requests refuse a link-out contract on the server as well as in the UI. Open **Sovra revenue (demo) → Co-op traffic** to see clicks per co-op, whether each co-op shares its member list, any contracts missing a contract-level link, and the switch for each co-op.

## Co-op memberships and fit scores

Results now have a **Co-op contracts for this** section, split into the co-ops an agency is on and the ones it could join. That split is the core of the partnerships spec: "when I'm looking for a laptop in Crested Butte, I need to see the co-ops I'm a member of and the ones I'm not."

Loci learns an agency's memberships without staff having to know them. Each agency has a website domain, and setting the agency runs a reverse lookup against the member lists Loci holds (`Coop.members` in `lib/coops.ts`). Matches come in as **detected** memberships, which count right away. Purchasing can confirm them, remove them or add a co-op by hand from the strip at the top of the section. NASPO ValuePoint works differently: agencies use it through their state's participating addendum, so a NASPO contract that lists the buyer's state counts as one the agency is on.

Every product card and co-op contract carries a **fit score** from 0 to 100: how much of the request it covers. Words in its name count fully, words only in its wider scope count 70%, and rarer words weigh more (`fitScore` in `lib/assistant.ts`). Sponsorship never changes a fit score. A priced option has to share a word for the thing asked for, not only a word for the kind of work: a software line sold with "annual maintenance" is no option for elevator maintenance, and "Platform management services" is none for janitorial services (`WORK_WORDS` in `lib/assistant.ts`). When a co-op the agency isn't on fits at least 10 points better than anything on its own co-ops, an amber flag says so. The comparison is by scope only, since price files aren't loaded for these contracts. A non-member contract offers **Ask purchasing to get us on this**, which logs a referral for that co-op and shows up on the Procurement home page as a join request.

Each co-op contract shown in results is logged as an impression, once per search. The ledger's **Co-op traffic** tab shows impressions, clicks and join requests per co-op, plus how many agencies matched its member list.

The laptop contracts behind the demo are real master agreements, carried as research leads because their current terms aren't confirmed. NASPO ValuePoint's Computer Equipment portfolio (lead state Minnesota) includes Dell 23004, HP 23011, Lenovo 23013 and Apple 23003. They were first taken from Dell's posted agreement and a Hawaii SPO vendor list; the co-op catalog (below) corrected Dell's number (Dell's own document says 23026) and added each award's dates and participating states. Sourcewell's technology portfolio includes 121923-CDW, whose August 2026 rate card lists 5% off notebooks, and 121923-IDL. Memberships for real agencies now come from the co-op directory (below). WSPC, and the Sourcewell memberships of the fictional Riverbend and Cedar Bend, are **demo lists for illustration**.

## The results page: a recommended route

A results page reads top to bottom as a procurement record: the request, one recommended route, every priced option, then the other sources.

**The request, as fields.** The top band shows what was read from the buyer's words: item, quantity, needed by, department, estimated total and agency. The words themselves sit underneath in small type ("Entered as: ..."). With no agency selected, the Agency field is flagged and a notice says eligibility isn't being checked.

**The recommended route.** One card names the route: the supplier and the contract it is bought under, a short summary, and four facts side by side: price, eligibility, requirement (P-card, purchase order, quote) and lead time. When another priced option costs less, a **Lower-cost option** line says so, with what it takes. Routes that have no published price (a quote under a co-op the agency is on, a co-op to ask purchasing about) are listed beneath as other routes. A **Not known** row says what isn't in the data: price files that aren't loaded, verification checks that haven't been run, research leads whose terms aren't confirmed. Each route cites its sources by reference number, and the same `Ref N` tag sits on the matching option or contract further down.

**Confirming the item.** When the top match fits the request closely (a fit of 80 or more), the route is shown straight away and the item is marked "matched, not yet confirmed"; **Change item or quantity** opens the confirmation step. When the match is weaker, the confirmation step comes first: the matching catalog items with SKU, supplier, contract, lead time and published price, a "different item, by quote" choice when co-op contracts cover the request without loaded prices, other products on the same contract, and a meter of the running total against the quick-buy limit. Confirming saves the quantity and the choice on the request.

**Purchasing options.** Every priced option is one row of a table, in ranked order: route and contract number, supplier and item, price each and in total, eligibility, requirement and lead time, with **Add to cart** and **Buy** on the row and the contract's own piggyback clause under **Details**. On a phone each row becomes a compact card.

**Other sources.** Everything else is folded to one row each, with a count: cooperative contracts, federal schedule contracts, products in co-op price files, contracts with no prices on file, a peer purchase on record, contracts not open to the agency, and issuing a solicitation. A section a person opens stays open while the page refreshes. For a buyer in a TRX state, that state's contracts stay open above the other sources, as the preferred route. With no agency selected, state contracts are one folded source among the others and don't lead the page or the route's sources.

**The purchase file** beside the route fills in as the buyer goes: request, items, options considered, route, basis and what's outstanding. It downloads as a text file. On a phone it sits below the options, with a bar at the foot of the screen that jumps to it and to the questions box.

**What the rules do and what Claude does.** The plan is rule-based (`lib/shopper.ts`): items and prices come from the listings, eligibility and membership from `buildResults()`, the P-card or PO call from the same test the result cards use. It runs in the browser, so it redraws as the order changes and works with no API key. With a key, Claude does two things (`lib/shopper-ai.ts`): it words the plan, and it answers questions in the **Questions** box ("Has TechSource been verified?", "What would it take to use Equalis Group?"). It works from a read-only packet of facts built by the rules and can't take actions; adding to the cart and asking purchasing are buttons. Every answer is checked before it's shown: a dollar amount or percentage that isn't in the packet, or a reference number that doesn't exist, discards the answer, and the rule-based wording stays. Without a key, the ask box says so and everything else works.

**Paperwork.** Once the route is shown, a **Paperwork** card drafts up to three documents from the purchase file: the justification memo, a quote request to the supplier under a co-op contract the agency is on, and a note asking purchasing about a co-op it isn't on. Each is a complete rule-based template with `[bracketed]` blanks (`lib/paperwork.ts`); the "From" line carries the signed-in person's name and the request's department. With a key, Claude tidies the wording (`lib/paperwork-ai.ts`); its version is kept only if every contract number, part number and blank survives and no new figure appears. The buyer edits, copies or downloads it. Loci never sends it.

Not built yet: proactive nudges, such as matching an expiring contract in the register to co-op contracts that cover it.

## Contracts: the explorer and a page per contract

For most requests the best Loci can surface is a contract a buyer may use, not an item with a price: the co-op catalog holds 31,930 contracts, and item prices come from a handful of them. So the contract is a record in its own right.

**Contracts** in the header (`/contracts`) searches every contract Loci knows: the co-op catalog's and the ones Loci holds itself (state contracts, agency registers, the demo contracts), 31,942 in all. Search by what a contract covers, who holds it, or its number. Filters narrow by kind (your agency's, state, co-op, federal), program, category, whether the agency can use it today, whether item prices are on file, and whether Loci can read one of its documents. With an agency set, contracts it can use come first, its own and state contracts ahead of co-ops; each row carries a tag: **You can use this**, **Needs a state addendum**, **Join to use** or **Not open to you**. Expired contracts and other agencies' register contracts are left out. The earlier list of contracts with prices loaded stays at `/vehicles`.

**Each contract has a page** (`/contracts/<id>`), reached from the explorer, the co-op section and quote-only cards on a results page, a supplier's storefront, and the agency's own-contract card. It answers what a buyer asks when there is no catalog item:

- **Can I use it?** The access line for the buyer's agency, with the reason, and the state-law note for co-op contracts.
- **How do I buy under it?** Numbered steps built from the record: join the co-op or confirm the addendum where that applies, ask the supplier for a quote that cites the contract, check the quote, order through the program. The steps are general practice, not terms read from the contract.
- **What does it cover?** The program's scope lines, and for GSA each SIN marked open to state and local governments or federal only.
- **Prices and items.** What kind of pricing is on file, said plainly (prices on file with their vintage, list prices before the discount, a discount off list, prices behind a member login, or none), and a searchable list of the contract's items where there are any. A list price is never shown as the contract price, and no discount percentage is shown.
- **What the documents say.** The documents on file, and for contracts Loci can read, a **contract brief** and **ask this contract**.

**The contract brief** asks the same six questions of every readable contract (what it covers, who can use it, how prices are set, fees, term and renewals, how to order), so two contracts can be compared field by field. It runs when someone presses **Read this contract**, and is cached. With a key, Claude writes one or two sentences per field and must quote the words they rest on; a field is kept only if its quote is in the cited passage word for word and every figure in the summary is in the passages. Otherwise, and without a key, the field shows the passage that bears on it most, or says the documents don't say. Lines with an email address or phone number are dropped from what's shown.

Loci can read a document for about 11,900 contracts: the price files it holds, master agreements published as files on the hosts in `DOCUMENT_HOSTS`, and GSA's contract terms and price lists under `/ref_text/` on GSA Advantage (its robots.txt bars only `/advantage/rs/`), fetched only when someone asks. OMNIA and TIPS documents are read only where a person downloaded the file. HGACBuy's document bundles are linked but not read, since they are zip archives.

## The shopper's tools: find a product, check a quote, ask a contract

**Shopper** in the header opens three tools that share one header.

**Find a product** (`/dive`) is a guided product search, and the engine under the home page's front door. The buyer says what they need in their own words, and the shopper builds a shortlist from the co-op catalog and Loci's listings, then asks questions that narrow it: a price band, the words that separate the products ("seat", "tube", "crew"), a maker, whether to show only what the agency can buy today. Every option is a real filter with a count, built from the products on the shortlist (`lib/dive.ts`), so an answer always narrows something. The buyer can also type ("under $2,000, and it should be a seat"). Each product shows its price and what kind of price it is: awarded bid, contract net price, or list price before the discount. Tick two or three to compare them side by side; **Plan this purchase** hands the product to the personal shopper on a results page. With a key, Claude reads typed messages into filters, choosing only from words and makers in the shortlist, and words the comparison (`lib/dive-ai.ts`). Without one, typed messages are read by simple rules and the comparison is rule-based. The shortlist puts what the agency can buy today first, then the product that is the thing asked for, then the agency's own state contract ahead of a co-op's: a New Jersey buyer's toner opens with NJSTART's. With no agency set, what any buyer could use comes before one state's contracts. The results page orders its products the same way. The dive is deepest where price files are loaded: playground parts, vehicles and seating.

**Specs.** Every served product name was also read for its specs (task `product-specs`, `scripts/product-specs.ts`; keys and wording in `lib/specs.ts`): fuel, drivetrain, cab, weight class, seats, age range, height, size, capacity, pack, color, material, back height, arms, print, speed and engine. A value is kept only when every figure in it and its words are printed in the product's name or price-sheet section, except a fuel or drivetrain read from an engine or model name ("5.7L Hemi V8" is gasoline), which is kept as inferred and shown as "from the model name". Spellings are made one ("b&w" is mono, "SuperCrew" is crew, 8' and 8ft are 8 ft). Review agents gave 7,441 values for 7,884 names and the check kept 7,423; 5,088 served products carry specs. The cards show them in a short line, the fit judge reads them, and the dive asks about them when the shortlist differs ("Which cab?", "Which arms?", "How high a back?"), with a removable spec filter for each answer.

**AI search: reading the request and judging fit.** With a key, two more model steps sit around the rule-based dive (`lib/dive-ai.ts`, wired in `dive()` in `lib/actions.ts`). Neither touches a price or who can buy; those stay the rules'.

- **Reading the request** (task `dive_understand`). When a dive starts, the model gets the buyer's words and up to 60 of the catalog's own product kinds that could match (`catalogKindCandidates` in `lib/catalog.ts`, from the kinds and aliases the product review gave every product). It picks the kinds the buyer means, other words a catalog may use for the thing (each candidate kind is shown with the other names the catalog uses for it, so the words come from the catalog's own vocabulary), the requirements the buyer stated and what they ruled out, and a one-line "read as". Kinds must be ones it was offered, other words must find products (a word that finds nothing is dropped without counting against the reading, since it can't mislead), a must-have must be in some product's name on the shortlist and can't be the kind itself, and a ruled-out word must be in a product's name or in what the buyer wrote. What passes widens the search (products of a chosen kind join the shortlist even when the request shares no word with their names, so "something for kids to climb on at the park" finds climbers) and becomes removable filters ("a crew cab pickup, not diesel" gives "crew" and "not diesel"). It runs alongside the request reader, so it adds no wait.
- **Judging fit** (task `dive_fit`). The rules' top 16 go to the model with each product's name, kind, maker and unit, never its price. It marks each one fits, partly fits or doesn't fit, with a reason of ten words or so ("A Charger is a sedan, not an SUV"). A reason with a price, a percentage or a figure that isn't in the product's name or the request is dropped. The verdicts reorder the shortlist within what the buyer can use (what fits first), and products judged not to fit are set aside under a closed "set aside" line with their reasons. Judgments are kept per request and per product, keyed by the product's line as the judge read it (name, kind, maker, unit, specs), so narrowing only asks about products not yet judged and a product whose specs change is judged again. Readings and verdicts are kept in memory and, with `DATABASE_URL` set, in Postgres (`lib/dive-memo.ts`, table `dive_memo`), each under the version of the prompt that made it, so a restart doesn't ask again and a changed prompt starts fresh.

The front door and `/dive` show the rules' shortlist at once and ask for the judgment in a second call (`judge: true`), then reorder when it arrives; a newer turn makes a judgment in flight stale. The results page's product section does the same: `getResults` returns the rules' products with any reading and verdicts already made (the dive's are shared, by the request's item and the product), and the page then calls `judgeResultProducts`, which reads the request if it hasn't been read, judges the top 16, and returns the section reordered with the poor fits set aside. A request that shares no word with a product's name can find products there too: "something for kids to climb on at the park" finds climbers where the rules found nothing. The "read as" line and the fit note carry thumbs up and down. Without a key, the dive and the results page work as before.

**Check a quote** (`/quote-check`) compares a vendor's quote with the prices Loci holds. The buyer pastes the quote or uploads it (PDF, DOCX, XLSX, CSV or text). Each line is matched by part number against the price files and Loci's listings, and the result shows the quoted price, the price on file, the difference, and the line of the price file it was checked against, with its page (`lib/quote-check.ts`). A list price is treated as a ceiling, not a contract price, and an awarded base price as a floor that options may add to. Lines with no part number, or a part number Loci doesn't hold, are reported as unchecked. With a key, Claude reads the quote's lines, and a line is kept only if its part number and price are printed in the quote. **Try a sample quote** builds one from real rows of Burke's price list, with two lines marked up and one part Loci doesn't hold.

**Ask a contract** (`/ask`) answers from a contract's own documents. Loci can read the three price files it holds and, for seeded contracts, master agreements and price files published as files on a short list of hosts (`DOCUMENT_HOSTS` in `lib/docs.ts`); it fetches those only when someone asks, and sites with bot walls or robots rules stay off the list. It finds the passages that bear on the question. With a key, Claude answers from those passages and must quote the words its answer rests on; a quote that isn't in the passage word for word is dropped, and an answer with no surviving quote is replaced by the passages. Without a key, the passages are shown. The first question on a document takes longest, since the file is read then and cached.

## Knowing whether the AI is right

The model does twelve jobs in Loci: reading a request, writing the buying plan, answering about a purchase, reading a product-dive message, reading what a buyer wants, judging how products fit, comparing products, wording paperwork, reading a quote, answering from a contract, briefing a contract and reading an uploaded contract. Each job's output passes a check before it is shown, and three things now measure how that goes.

**A log of what was kept and what was thrown away** (`lib/ai-log.ts`). Every model call ends one of four ways: kept, kept in part (some quote lines, quotes or brief fields failed their check), discarded by a check, or failed (an API error, a refusal, an answer cut off). The log records which, why, how long the call took, a line saying what was asked, and what the model wrote, cut short. It also records when a kept answer said the data doesn't hold what was asked. Each record carries a fingerprint of the model and system prompt, so results can be compared across a prompt change. The log is separate from the app's state: it is never sent to the browser with `/api/state`, and a demo reset doesn't clear it. It keeps the most recent 5,000 calls in memory, and in a Postgres table (`ai_log`) when `DATABASE_URL` is set. Calls made with no API key aren't logged.

**A thumbs up or down on each answer** (`components/Feedback.tsx`). "Was this right?" sits under the buying plan, each shopper answer, the side-by-side comparison, a drafted document, the quote check, the contract brief and each contract answer, whenever the model wrote what is shown. Rule-based text has no thumbs. A thumbs down can say what was wrong. The vote is stored on the log record for that call, one per browser or account, and no account is needed.

**AI quality** (`/quality`, in the account menu) reads the log. For each job it shows the calls made under the prompt in use now, the share kept whole, the counts kept in part, discarded and failed, how often it said it didn't know, the thumbs, and the most common reasons output was discarded, with one line for earlier prompts. Signed-in people also see the recent calls worth a look (discarded, kept in part, failed or marked wrong) with what was asked and written.

**Tokens and the prompt cache.** Every call records the tokens the API counted: uncached input, output, and input written to or read from the prompt cache. `/quality` totals them by task. `structured()` marks each system prompt for the cache, and callers can pass `shared`, text sent ahead of the rest of the message because it repeats from call to call. The shopper's answers send the request's FACTS that way, so a follow-up question reads nearly all of its input from the cache, billed at a small fraction of the normal rate. The structured-output schema is part of the cached prefix, which is what takes most tasks past the 512-token minimum. A prefix below the minimum is simply not cached. The buying plan is saved instead (`lib/shopper-ai.ts`): a plan that passed its check is kept in memory by the facts and prompt it was written from, the last 500 of them, so a reload, or a colleague opening the same request, shows it without another call. Different facts, such as a new selection, get a new plan. Caching can't link the plan with the follow-up answers: the structured-output schema comes ahead of the system prompt in the cached text, and the two tasks' schemas differ.

**A fixed test set** (`npm run eval`; cases in `evals/cases.ts`, runner in `scripts/eval.ts`). It holds 74 cases built from the seed, so none depends on the network or on what anyone has done in the app. 41 are guard cases: each hands a check output that is known to be right or wrong (an invented price, a discount that isn't on file, a quantity passed off as a price, a reference that doesn't exist, a misquoted clause, a price taken from another line of a contract, a filled-in blank) in place of the model, and says what the check must do with it. They need no API key. 33 are live cases: each sends a fixed input through the real prompt and grades the answer (did it survive its check, does it give the total on file, does it say it doesn't know what the documents say about installation, does it answer a question that names a price that isn't on file). They need `ANTHROPIC_API_KEY` (in a Claude Code cloud session, which drops that name from the shell, set `AGORA_ANTHROPIC_API_KEY` instead). The run is compared with `evals/baseline.json`, names any prompt whose fingerprint has changed since, and exits with an error if a case fails that passed before. `--runs 3` repeats each live case: a case passes only if every run does, its pass rate (2/3) is printed, and each job's line counts how often its output was kept whole, kept in part, discarded, failed or never sent to the model. `--save` records a new baseline, with the pass rates when `--runs` is above 1, and a later run with a lower rate says so. `--guards` runs the half that needs no key, and `--only <text>` picks cases by id or job. A case the API never answers (a rate limit, an outage) is reported as not run and left out of the score and the saved baseline, and a refused key stops the run before anything is saved, so a bad key can't record the live cases as known failures. The committed baseline was saved against the model on November 15, 2026, with three runs of each live case.

## Agency setup, plans and the free tier

**Procurement → Setup** (`/procurement/setup`) is where a purchasing admin configures an agency once, so staff never have to. It shows a three-step checklist (state, the agency's own contracts, co-op memberships), the membership strip, the contract register and the plan.

**Contract register.** The admin uploads a CSV or XLSX with one contract per row. `lib/register.ts` finds the header row by common column names ("Contract Name", "Vendor", "Contract #", "End Date", "Not to Exceed" and so on) and validates every row. A row with no title, no vendor, an unreadable date or a ceiling that isn't a single amount is not imported, and the report names the row and the reason. An expired row is imported but hidden from search. Re-uploading updates rows by contract number instead of duplicating them. Register contracts belong to that agency alone: `/api/state` strips other agencies' rows before anything reaches the browser, and search never shows them to anyone else. When a request matches one, results open with **"Your agency already has a contract for this."** **Try the sample register** loads `public/test-contracts/harmon-lake-contract-register.csv`: eight rows, with three broken on purpose and one expired.

**Free tier.** Search is always free. The free plan includes 5 published RFPs a year (`FREE_RFP_LIMIT` in `lib/agency.ts`), and the counter resets each year. At the limit, RFP Lite asks the agency to upgrade, while search and handoffs keep working. Harmon Lake Township is seeded with 4 of 5 used, and Riverbend, a city marketplace customer, is on the paid plan. The free plan shows sponsored placements, marked as sponsored. A paid agency can turn them off for its staff, which drops both the label and the ranking nudge.

**When nothing fits,** results offer three next steps: **RFP Lite** (free, counted against the plan), **Sovra's full RFP tool** (paid) and a handoff to the agency's own tool (Euna, OpenGov or Bonfire). Handoffs are recorded but don't call any outside system.

**Setup questions route to purchasing.** If a requester searches before setup is done, a one-line banner says what's missing and what that means for the results, and offers **Invite purchasing**. The invite shows up on the setup page. No email is sent in the demo.

Results also hide expired contracts by default, behind a one-line "N expired contracts also matched" with a **Show** link. State contracts in TRX states (New Jersey, Oregon, Arkansas, Hawaii and New York; `TRX_STATES` in `lib/trx.ts`) carry a **TRX** label everywhere they appear, and the ledger books a TRX fee only on those. Other state contracts show an ordinary transaction fee. TRX contracts are the route Loci prefers: New Jersey's (from NJSTART), Hawaii's (from the State Procurement Office), Arkansas's (from the Office of State Procurement) New York's (from the Office of General Services, plus its preferred sources and the county cooperative Empire Procure Connect) and Oregon's (DAS's statewide price agreements on OregonBuys) are loaded, and each leads results for its own state's buyers (see **NJSTART**, **Hawaii**, **Arkansas**, **New York**, **Empire Procure Connect** and **Oregon** below).

## The co-op directory and the Co-op data page

Loci's co-op memberships for real agencies come from a public cooperative purchasing workbook, collected November 13, 2026 (`seed/coops/source/coop-memberships-2026-11-13.xlsx`). It has 90,469 published roster listings from Sourcewell, HGACBuy, BuyBoard (Texas and National), Mohave, E&I and COSTARS, plus Texas DIR sales by buyer, NASPO and OMNIA contract-access listings, agencies' own published co-op relationships and documented purchases. CISA's .gov registry (`seed/coops/source/dotgov-domains-2026-11-13.csv`, federal domains and contact emails removed) adds domains.

`npm run import:coops` (`scripts/import-coop-data.ts`) builds three files from them:

- `seed/coops/directory.json.gz`: about 121,000 governments, one record each, with their federal IDs, co-ops, the evidence for each, websites, population or enrollment and DIR spend. Churches, private schools and nonprofits are set aside. A government whose source doesn't classify it is kept only when its name reads as government, and it's marked "inferred".
- `seed/coops/insights.json`: the numbers behind the **Co-op data** page.
- `seed/catalogs/naspo-contract-access.json`: NASPO ValuePoint's Parks and Recreation awards with their participating states, and local governments that signed their own addendum.

**More rosters.** `npm run fetch:rosters` (`scripts/fetch-rosters.ts`) saves co-op rosters published after the workbook into `seed/coops/source/rosters/` as CSVs in the workbook's columns, and the importer reads them alongside its roster tabs. It now carries Choice Partners' public member table: 2,755 listings, 2,454 kept, 2,399 governments after merging, 414 of them new to the directory. It also carries 1GPA's published membership workbook, dated August 28, 2023, which was saved by hand because Dropbox serves it from a one-time host: 1,304 listings and 1,171 governments, 147 of them new, flagged as a historical snapshot (a listed member may have left since). TIPS, OMNIA, Equalis, NPPGov and PEPPM offer lookup tools or vendor-only exports, not open rosters.

**Permanent IDs.** `npm run fetch:federal` (`scripts/fetch-federal-ids.ts`, needs www2.census.gov and nces.ed.gov) downloads the Census Bureau's Government Units List 2026, the NCES Common Core of Data district directory for 2024-25 and IPEDS 2024 into `seed/coops/source/` as gzipped CSVs. It keeps IDs, names, places, websites and sizes, and leaves out officials' names, phone numbers and street addresses. The importer matches every directory entry to one federal record (Census `CENSUS_ID_PID6`, NCES `LEAID`, IPEDS `UNITID`) and merges entries that share an ID. Census school districts are paired with their NCES records by website or expanded name, and same-named townships are told apart by county. A name that says Town never matches a record that says Village when both exist. Every government in the registries joins the directory, roster or not, which brings it to about 121,000 governments, 100,000 of them with an ID and 47,000 with a website. IPEDS also sets aside the private colleges on the E&I and BuyBoard rosters. `/api/directory?id=census:210967` (or `nces:` / `ipeds:`) finds a record by federal ID.

Listings without an ID are joined by `entityKey` in `lib/coops.ts`, the same function the live matcher uses. It lines up "Plano ISD" with "Plano Independent School District" and "Lawrence, City of" with "City of Lawrence", but keeps City of Plano and Plano ISD apart. The directory is server-only (`lib/directory.ts`), so it never reaches the browser; `/api/directory?q=` serves the agency typeahead and `?id=` serves one record.

**What it changes in the app.** "Your agency" now offers a search over every government in the directory. Picking one, or setting an agency the directory recognizes by website or by name and state, brings in its co-ops as detected memberships. Each carries its **evidence**: on a published roster, named on the agency's own procurement pages, or bought through it (an approved award or DIR sales). The membership strip in results shows the evidence and the member ID where one was published. Loci now tracks 19 real co-ops, up from two. An uploaded member list can't remove a membership that rests on stronger evidence. Ten NASPO Parks and Recreation awards are in search as quote-only research leads, and `Eligibility.adopters` lets a local government with its own addendum (San Joaquin County, City of Albany) use a portfolio its state hasn't signed.

**Guide** (`/guide`, in the account menu and the footer) is the short version for a buyer: how to use Loci in five steps, what its terms mean (routes, eligibility and paying, price kinds, and the evidence and flags behind what it says), where the contracts, prices, member lists and state rules come from, and the questions asked first. Its counts and dates are read from `seed/coops/insights.json`, `seed/catalog/insights.json` and `lib/state-rules.json`, and it links to the Co-op data page for the full account.

**Co-op data** (`/data`, in the account menu) explains all of this for leadership. It covers what's in the workbook, the five ways Loci uses it, a live agency lookup, the evidence ladder, documented purchases, a prospect list (the largest DIR buyers already on several co-ops), cautions (including six NASPO awards whose addendum states disagree with Loci's seed) and the data still needed, led by a government ID spine.

**State rules.** Whether a city or school district may buy off a co-op contract is a matter of state law. Loci's 50-state research of November 13, 2026 (`seed/states/source/`: the report and its summary workbook) covers, for each state:

- the authority for local governments and for school districts;
- any state-approved list (only Alabama and Mississippi run true lists);
- the conditions: board action, and what the lead contract must be;
- exclusions, construction above all;
- quote and formal-bid thresholds.

`npm run import:state-rules` (`scripts/import-state-rules.ts`) builds `lib/state-rules.json` from the workbook's tables and each state's report section, with its statute links. The file is server-only (`lib/state-rules.ts`), so results carry just the buyer's state. **Co-op contracts for this** shows a **State law** note: the authority line for the buyer's kind of government, its conditions and thresholds, an openness grade from 1 to 5, and a red warning when the request looks like construction. `/data#states` lists all 50 states with the full sections. The research's flags (`[mirror]`, `[secondary]`, `[unverified]`, `[currency unconfirmed]`) are kept and shown, because many points were read on third-party mirrors. None of this is legal advice, and it doesn't change routing; the agency's own quick-buy limit still decides.

## The co-op catalog

The membership directory says which co-ops each agency is on; the co-op catalog says what those co-ops have under contract. It's a capture of 13 co-ops' public contract directories, supplier lists, product tables and price files, retrieved November 13, 2026 (`seed/catalog/source/`, with its own README, coverage and validation notes): 31,930 supplier contracts, 34,619 products in 39,503 offerings and 12,602 price-document links, from Sourcewell, OMNIA Partners, TIPS, BuyBoard, HGACBuy, NASPO ValuePoint, Equalis, 1GPA, Choice Partners, E&I, PEPPM, NPPGov and cooperative-flagged GSA MAS listings.

**GSA is stashed, not served.** GSA's 12,473 schedule contracts brought no products (GSA Advantage's item pages are off limits to automated readers) and crowded search, so the importer leaves them out unless `AGORA_INCLUDE_GSA=1`. Their rows stay in the source files, GSA's own files (`gsa-sins.json`, `gsa-mas-contracts.csv.gz`, written by `npm run fetch:gsa`) are in `seed/stash/gsa/` with a note on bringing them back, and the app still knows how to show them (a GSA lane on results, the explorer's "Federal (GSA)" filter, SIN-level access). The demo's fictional Patriot Supply GSA contract is part of the walkthrough and stays.

**Most products are stashed, not served.** The catalog had 59,362 products, and most could not show what Loci is for: 37,411 of its 69,528 offerings had no price, and thousands more were rate lines or component parts that crowded every search. The importer now serves 8,141 products in 10,029 offerings and leaves out 51,195. Three hard rules come first: no price (531), a co-op whose items carry none (PEPPM's 21,413 behind the member login, HGACBuy's 9,611 discounts with no list price), and lines priced by time (3,292, with service awards such as airfare and staffing). Then the product owner's rule for services: a service sold as a fixed package (a 3-year service plan, an installation package, a vehicle wash, surface treatment by the square yard) counts as a product, while a time-based rate, a line that mixes goods with labor, or one agency's own project line item does not. A second review (task `package-check`) gave 1,807 service and project-like lines a verdict (1,228 package, 142 product, 344 project, 75 rate, 18 mix); 419 are kept out as not a package. Then the AI review's role decides wherever it gave a confident answer (below): whole items and consumables are served; 4,538 parts and accessories and 288 rates and services with no package verdict are not. A low-confidence answer counts only one way: when it says a product is a part, an accessory, a rate or a service, the product stays out (552), but a doubtful "item" never brings one in. Patterns decide the rest: 8,841 Burke components by part-number family, 1,634 Canon lines in its software and licence sections (these stay out whatever a reviewer said, since reviewers split on licences; its service plans are judged as packages), and 76 items on New York's crash-mitigation award. The rule is `scripts/product-stash.ts`, and `seed/stash/products/` has the counts and a note on bringing them back (`AGORA_INCLUDE_STASHED=1`). Contracts are never stashed, so those co-ops' contracts still appear as routes. The cost: **Check a quote** can't price a line against a stashed part.

**What each product is.** Every priced product name, served or stashed, was coded through the AI review loop (task `product-kind`, `scripts/product-kind.ts`), in two batches of review agents: 16,166 names. Each answer gives the product's kind, the phrase a buyer would type for it ("pickup truck", "swing", "toner cartridge"); its role (a whole item, a part, an accessory, a consumable, a rate or a service); and up to four other names buyers use ("can liner" for a trash bag, "park bench" for an outdoor bench). The collector keeps an answer only when every word of the kind appears in the product's own record (its name, maker, contract or price-sheet section), so a kind is named from the data, never invented. 15,900 answers passed (8,530 high, 5,597 medium and 1,773 low confidence), and the importer applies the high and medium ones to 14,412 products. Left to rules without review: products with no price, Burke's hardware families (part numbers under 200) and lines priced by the hour, day or month.

The role decides the stash (above), which brought back products the patterns had wrongly kept out: Canon's copiers and inks, New York's whole crash cushions, barricades and channelizer drums, and Burke's climbers and slides. It also took out parts and add-ons the patterns had let through, such as print heads, battery-box keys, swing seats and vehicle options. Search uses the kind and aliases two ways. They join a product's searchable scope, so "park benches" finds Burke's benches and "pickup trucks" finds BuyBoard's Ram and Colorado pickups, whose names say "Truck". And a product that *is* the kind asked for ranks above one whose name only mentions it (`kindMatch` in `lib/assistant.ts`): for "a swing", Burke's swings lead and the swing hangers fall below. A product with no confident answer is ranked by the phrase its name opens with.

`npm run import:catalog-coops` (`scripts/import-catalog.ts`) builds `seed/catalog/catalog.json.gz`, `insights.json` and `reconcile.json`. The capture listed suppliers by exact name, so the importer merges records whose names match once legal suffixes are dropped, or that share a company website: 24,094 records become 22,778 companies (seven more merged by the review below). Links that every contract shares (TIPS, BuyBoard and 1GPA point all their contracts at one directory page) are kept as directory pages, not contract pages. The catalog lives on the server (`lib/catalog.ts`), with a word index so a search over it takes milliseconds.

**Search and the co-op section.** Results add the best-fitting catalog contracts to **Co-op contracts for this**, scored with the same fit formula, split by the agency's memberships (NASPO contracts count when they list the agency's state), at most 8 per side with a count of the rest, and one card per supplier per co-op. Expired contracts are hidden; contracts without a published end date say so. GSA MAS listings, when included, get their own lane with a SIN caveat. Contracts Loci already seeds are skipped. Clicks go through the tracked `/go/[contract]` redirect; a contract with only a directory page links to that page with its number to look up. **Ask purchasing to get us on this** works on catalog contracts and keeps the number and supplier on the referral.

**Products.** **Products on co-op contracts** shows catalog items matching the request, each with every contract that sells it and its price or labelled list price: the state programs' awarded prices, vehicle awards, Canon's machines and supplies on Sourcewell, Burke's freestanding playground items and SitOnIt's list prices. Items with no price are stashed (above). Items listed under several SKUs collapse to one card. **View on …** goes through `/go` to the exact item page.

**Program pages.** Every program in the catalog (the seven state programs and twelve co-ops, GSA stashed) has a page at `/programs/[slug]` (`/programs/njstart`, `/programs/sourcewell`; a catalog id such as `/programs/state_nj` settles on the slug), built like a storefront by `lib/programs.ts` and served by `/api/catalog/programs`. A page counts only current contracts. It shows the program's one-line description (the only hand-written copy, in `ABOUT`), how a local government buys through it (the TRX steps from `lib/trx.ts` for state programs, membership or NASPO's participating addenda for co-ops), where the visitor's agency stands, what's on contract by Loci's categories (or by the program's own headings where most of its contracts have none), a sample of priced products one per kind, each labelled with what its price is, the suppliers with the most contracts, and every contract, searchable and filtered by category, the agency's open ones first. `/programs` lists them, state programs first. A contract page's program name links to its program page. The descriptions were checked on November 16, 2026 against the sites that could be read from a cloud session (NJSTART, OGS and its preferred-sources page, OregonBuys, Hawaii SPO, Arkansas) and against published sources for PEPPM, 1GPA, Equalis, E&I, NPPGov and Empire Procure Connect.

**State contracts' categories.** The state programs' contracts now carry Loci's categories too, through the same review (task `category`, keyed by title): 921 state contract titles not reviewed before were answered on November 16, 2026, and the importer applies a pick to any state contract its program's records don't already settle (NJSTART's commodity groups still win). Of the current state contracts, 4,124 of 4,213 now have one; NY Preferred Source's vague section names leave 12 of its 42 without. In search this changed one TRX lane among nine requests checked: New York's heavy-equipment rental award no longer turns up for road salt.

**Storefronts.** Every catalog company has a storefront at `/storefronts/cat_…`, built from its contracts, with the agency's own co-ops first. **Claim this storefront** brings it into Loci as a supplier, so the usual claim flow (a work email on the company's website domain verifies at once) applies. Loci's own suppliers show an **On co-op contracts** section from their catalog record, and `/storefronts` searches all 22,778 companies.

**Browse.** `/browse` ("Everything in Loci") is the whole shelf by category: Riverbend's buyable listings first, then every catalog product on a co-op or state contract, a page of 50 at a time from `/api/catalog/browse` (`catalogBrowse` in `lib/catalog.ts`), priced items first, each with its best price on file, its program (TRX, state or co-op), its supplier's storefront and its contract page. A product takes its contract's category, or failing that the contract's NIGP class, or the words its price was filed under. Each category links to its contracts in the explorer (`/contracts?category=…`). The home page's counts (contracts, suppliers, products, programs, and each category tile) add the catalog's totals from `/api/catalog/summary` to Riverbend's own.

**Price-list queue.** Account menu → **Price-list queue** (`/coops/price-lists`) lists the linked documents by co-op and kind (with GSA stashed, mostly HGACBuy document bundles, Canon's Sourcewell price PDF and the state programs' documents). **Read it** opens the contract upload page with `?document=…`; the server fetches only documents in the catalog (15 MB and 25 seconds at most), reads it with the contract reader, which now reads HTML price tables as rows, and fills any header it can't find (supplier, contract number, co-op, dates) from the catalog. Each read's outcome shows in the queue. Nothing publishes until the rows are reviewed.

**Item prices from co-op price files.** Most co-ops publish discounts, not item prices: of 50 Sourcewell price files sampled, only Canon's lists items. GSA's linked documents are contract terms and labor rates, and HGACBuy's bundles are executed contracts. Some files do list real item prices, though. `npm run import:price-files` (`scripts/import-price-files.ts`, PDFs need `pdftotext`) reads the ones saved in `seed/catalog/source/price-files/` into `seed/catalog/price-rows.json`, and the catalog importer attaches each row to its co-op contract and supplier. It starts with two files:

- **BuyBoard 724-23:** the vehicle award report, with 452 awarded base-model prices (only rows marked Yes). These are December 2023 award prices for the December 2023 to November 2024 period, and the contract ends November 30, 2026, so they're labelled as awarded bids, not current quotes.
- **NASPO ValuePoint 204521:** Endera's base price for each cutaway transit bus class, before options and delivery.

- **OMNIA Partners R220201:** BCI Burke's 2027 price list (244 pages), with part number, description, list price and the OMNIA net price on each line. A person downloaded it, since OMNIA's robots.txt bars Claude's crawler. The contract's net is list less 7%, and a row is kept only when its two prices agree, which drops 193 rows where the PDF's text layer pairs a list price with another row's net. That leaves 11,456 parts, from bolts and swing seats to full play structures, each shown at its contract price with its list price. These are 2027 prices.
- **NASPO ValuePoint MA3964:** SitOnIt's November 2024 price book (657 pages). ## NJSTART: New Jersey's state contracts, preferred for New Jersey buyers

NJSTART is New Jersey's purchasing system, and its state contracts are the TRX program Sovra supports. A New Jersey town, county or school district may buy on any state contract the state opens to its Cooperative Purchasing Program: the state already bid it, so the local unit doesn't advertise for bids of its own, and it carries the lowest fee of any shared contract. **The data.** All 1,437 active NJSTART contracts, read from the state's public list on November 14, 2026 (one internal record whose vendor is the state itself is skipped). ## The document store: every TRX document's text, searchable

The text of every document linked to a TRX program's contracts lives in Postgres with a full-text index (`lib/doc-store.ts`), so search can find a contract by what its documents say. With `DATABASE_URL` set, the server fills it in the background (`lib/doc-ingest.ts`, started from `instrumentation.ts` a minute after boot): it records which contract links to which document (34,611 links, 27,187 URLs, 4,160 contracts), stores the text Loci already holds (`seed/catalog/doctext`) without fetching, then fetches the rest from their publishers through `lib/doc-fetch.ts`, two at a time per host with a pause between requests, price sheets first. It resumes after a restart; failures are retried after a day, three times at most. Identical text is stored once (many NJSTART attachments repeat the same standard terms), and long pages are stored in parts. It stops at `AGORA_DOC_DB_LIMIT_MB` (4,000 by default, short of the 5 GB volume). `AGORA_DOC_INGEST=off` turns it off; `AGORA_DOC_FETCH_LIMIT` caps fetches per host for a test run. `/api/docs/status` reports progress (counts only).

What uses it. **Search results** and the **contract explorer** take contracts whose documents contain every word of the request as candidates, with a fit in the 60s so a contract whose title matches still leads, and show where the words were found ("Found in T0077 State-Supplied Price Sheet: …"). **Ask a contract** reads its usual documents and adds the pages that best match the question from all of the contract's stored documents. The document reader reads stored text before fetching, and stores what it fetches. **Scans.** PDFs with no text layer (signed agreements and amendments, about one in six files on the live site) are read by Claude (`lib/doc-ocr.ts`), alongside the fetching, six at a time (`AGORA_OCR_WORKERS`), when the server has an API key; a reader whose request went unanswered pauses a minute. Each scan is split into runs of ten pages and sent through `structured()` as the `scan_text` task; the prompt asks for a transcription exactly as printed, table rows on one line, `[illegible]` for what can't be read. The check keeps a page only if it is one of the pages sent, comes back once, and carries text (or is marked blank); a run the model can't answer whole is tried again in halves. The text is stored like any other, marked `via = 'scan'`, with the model that read it in `read_by`. Scans go to the smaller model in `SCAN_MODEL` (`lib/llm.ts`; `AGORA_SCAN_MODEL` overrides it), since most only need to be searchable. The first few hundred were read by the main model (`MODEL`) before the switch; those are kept as reference transcriptions, to check the smaller model's readings against. `lib/scan-compare.ts` does that check: with `AGORA_SCAN_COMPARE` set to a sample size, the server re-reads that many reference scans with `SCAN_MODEL` (half of them price sheets, nothing stored overwritten) and compares words, numbers and dollar amounts, flagging amounts that differ by one digit or two swapped digits as misreadings. `/api/docs/status` reports the result under `scan_compare`. It stops at `AGORA_OCR_PAGE_LIMIT` pages (150,000 by default), and stops itself if the first ten scans all fail; `AGORA_OCR=off` turns it off. Each scan is tried three times at most. A scan pdf-lib can't split (a malformed file) is sent whole when it is 20 pages or fewer. Old Word (`.doc`) files are read with `word-extractor`; PowerPoint decks slide by slide, macro-enabled workbooks (`.xlsm`, `.xlsb`) as workbooks, RTF and plain text as text, and zip bundles by reading each file inside (up to 40, headed by the file's name). JPG and PNG attachments are images of pages, so the scan reader wraps each in a one-page PDF and reads it. A download with no extension is typed by its first bytes. The ingest takes files up to 40 MB, and spreadsheets up to 20 MB, since they swell many times over when read (the reader, which a person waits on, stays at 15 MB). The ingest shares the web server's process, so it guards it: each file is marked as attempted before it is opened, so a file that brings the server down is passed over after the restart instead of crashing it again (a 100 MB limit did exactly that once, on November 15), and a reader waits while the heap is above `AGORA_DOC_HEAP_PAUSE_MB` (2,500). Files of a type Loci didn't read, or over the size limit, are tried again after each deploy, three times at most. `/api/docs/status` breaks the documents that haven't become text down by file type and reason (`store.problems`). Without `DATABASE_URL` (local runs, the rehearsal) none of this runs and search works as before.

## Item prices from the state programs' price sheets

NJSTART, OregonBuys and Empire Procure Connect attach price sheets to their contracts: about 3,400 of NJSTART's attachments and 470 of OregonBuys' are labelled as price sheets, price lists, pricing or schedules of prices (`isPriceSheet` in `lib/price-sheets.ts`; OregonBuys' summary pages and terms are left out). The document store holds their text, and `lib/price-sheets.ts` reads it into item prices on the server.

**The reading.** Each sheet's text goes to the smaller `SCAN_MODEL` in runs of about 14,000 characters, through `structured()` as the `price_sheet` task. Every run after the first carries the sheet's opening lines (its title and column headings, up to 25 lines) as context, so the model can tell which column is the price and what kind of price it is; rows are taken only from the run itself. (Until November 15 later runs went without them, and on long sheets the model took list prices for contract prices, and once a weight for a price.) The prompt asks for one row per priced item: what it is, its unit, the price, the basis (contract price, net price, not-to-exceed rate, list price or discount) and the line that prints it, copied exactly. A scanned sheet read by the smaller model is first read again by the main model (`readScan(…, MODEL)`), and the new reading replaces the stored one, so no misread digit becomes a contract price. A sheet linked to more than one contract is passed over, since its rows can't be pinned to one supplier.

**The check.** A row stands only when its line is in the sheet's text (spacing and case aside), the price is one of the figures on that line and not a percentage, the line has words and names the item, and the line isn't a total or an estimate. Discounts are dropped, since they wait on the product decision. List prices are kept, marked as list prices: the catalog shows them as "List $X · before the contract discount", never as the price a buyer pays, and they are the base for net prices once discounts are decided. Sheets read before list prices were kept are read again ahead of the rest, found by the list prices their records say were dropped; each one's old rows are cleared just before it is read, so a stopped run loses nothing. (The first version cleared them all up front, and on November 15 a run stopped during a deploy left 159 sheets cleared and unread. `AGORA_PRICE_SHEETS=restore` reads those: the unread sheets that come before the last sheet read, since every run takes sheets in the same order, by the MD5 of their URLs.) Each run reports with `pieces()`, so `/quality` shows how many proposed rows survived.

**Running it.** `AGORA_PRICE_SHEETS=sample` on the server reads 25 NJSTART and 15 OregonBuys sheets (two minutes after start) and reports the yield; `AGORA_PRICE_SHEETS=500` reads that many sheets not yet read and stops, and `AGORA_PRICE_SHEETS=all` reads every sheet not yet read, eight sheets at a time (`AGORA_PRICE_WORKERS`) with four parts of each sheet sent at once (`AGORA_PRICE_PARTS`), and picks up where it left off after a restart. Rows go to the `doc_prices` table, one record per sheet to `doc_price_reads`, and progress to `price_sheets` on `/api/docs/status`. `/api/docs/prices` exports the rows a page at a time.

**Into the catalog.** `npm run import:doc-prices` pulls the export from the live site into `seed/catalog/source/doc-prices/rows.json.gz` (`-- --db` reads a local database instead), and `npm run import:catalog-coops` folds the rows in as products and priced offerings on their contracts, labelled with the sheet's name and the date it was read ("Contract price on "T2466 Thales Price Sheet 2.27.26", read Nov 15, 2026"), with the line kept in the offering's detail; a list price goes in the offering's list field, with no price. The importer checks every row again. Amendments often reprint a contract's whole schedule, and an older sheet's lines can wrap differently from the newer one's, so only a contract's latest sheet stands, ranked by the amendment, revision and date in the sheets' names; sheets the names can't rank stand together unless they print different prices on the same line, and then that line stays out. A row whose contract already has the same price for an item of the same name (NJSTART's line items) is left out as a duplicate. Rows from a long sheet read in parts without its headings (every reading before the fix; the export says which, with `headed` and `whole`) stay out, and so does every row of a sheet whose rows mix list prices with contract prices, since such a sheet disagrees with itself about its columns. `insights.json` counts the rows kept (and how many are list prices), superseded, unclear, duplicated and rejected (`doc_price_*`).

**What is in the catalog** (November 15). About 600 sheets were read, then the long ones were found to have been read without their headings. The catalog carries the rows from the sheets read whole: 2,490 offerings from 98 sheets on 89 contracts (1,997 contract prices and 493 list prices), which took the catalog from 56,924 products to 59,362, and from 25,020 priced to 26,966. 35,820 rows from long sheets wait to be read again with the headings.

**What the local sample showed** (November 15, a partial copy of the store): of 25 sheets, 10 printed item prices. OregonBuys' security-services agreement reprints its schedule in each of ten amendments, and the latest sheet's 60 rates stood while 358 older rows were set aside. NJSTART's "State-Supplied Price Sheet" files are often the state's blank bid form, with no prices filled in, and correctly give no rows.

## Reading the state programs' documents

"Ask a contract" and the contract brief can read every document linked to a TRX program's contracts, in two ways.

**Held text.** `npm run import:doctext` stores the text Loci already has, keyed by the document's URL, in `seed/catalog/doctext/<program>.json.gz` (about 6 MB in all), with PDF pages kept so answers cite page numbers: Hawaii's 107 lists, notices and schedules; Arkansas's 97 documents with a text layer (spreadsheets as rows); New York's 307 award documents (PDFs and spreadsheets), the OGS master list, the preferred-source list and Corcraft's price guide; and each NJSTART, Empire Procure Connect and OregonBuys contract's summary page. The documents' own contact details (contract managers, phone numbers, emails) are kept, at the product owner's instruction. `lib/docs.ts` reads held text first, without fetching, loading the stores on first use.

**Live fetch.** For anything not held or stored (NJSTART's 18,635 attachments, OregonBuys' 5,210, EPC's 534), the reader fetches the file when someone asks, from the hosts in `DOCUMENT_HOSTS`. The state hosts were added after checking their robots rules on November 14, 2026: Arkansas allows all; OGS bars only admin, login and search paths; Corcraft has no robots.txt; NJSTART and EPC redirect theirs to their vendor's, which bars only `/craft`. NJSTART and EPC serve files through a download action rather than a file path, so the reader accepts those links and takes the file type from the `Content-Disposition` name. Scanned PDFs with no text layer still can't be read (one EPC addendum in testing, 18 of Arkansas's originals).

New York contracts now link their award's own documents (how to use, pricing, specifications, contract updates), NJSTART and EPC contracts link their summary pages, and Corcraft's records link its guide. Every contract in the six TRX programs has at least one readable document: 30,750 documents across 3,509 contracts.

## Co-op member lists

**Co-op member lists** (account menu, or **Ledger → Co-op traffic**, at `/coops`) is where Sovra ops keeps each co-op's list of member governments. Upload a CSV or XLSX with one government per row. `lib/members.ts` finds the name, website, email and state columns by their usual headings. A website, or failing that the domain of a contact email, is what Loci matches on. A row with neither still matches by name within the same state. Rows with no name, an unknown state or nothing to match on are skipped and reported. **Add to list** merges the upload into the existing list; **Replace list** swaps the list out entirely.

After every upload, Loci re-runs the lookup for every agency it knows. Newly matched agencies get a detected membership, so the co-op moves to **Co-ops you're on** in their results. A detected membership that nobody confirmed is dropped when its agency no longer appears on the list. The page also adds co-ops Loci doesn't track yet (TIPS, for example). **Try the sample** loads `public/test-contracts/sourcewell-member-list-sample.csv`: eight fictional rows, including one matched by email domain, one by name and state, and two broken on purpose.

## Carts, approvals and orders

Result cards and product pages have **Add to cart**, and the header shows the cart. Each person has one open cart (`owner` on the cart): an account's, or, before signing in, the browser's, whichever agency they're buying for. A visitor's cart has no agency. When they sign in or sign up it moves to their account, merged into one the account already has open, and is attached to the agency they're buying for; it follows that agency until checkout, where every line is checked against it. Visitors' carts untouched for 30 days are dropped. The browser receives only its own drafts; carts sent for approval are the agency's and go only to its signed-in people. The **cart** (`/cart`) splits by supplier, and each supplier's share is paid one way: P-card under the $10K quick-buy limit, a PO at or over it. Whoever built the cart can **hand it to someone who can buy**, with a division, a delivery address and notes, because the person who needs something often isn't the card holder. A cart with any PO share goes to Purchasing on **Send for approval**. Otherwise it orders right away. Purchasing approves it from the Procurement home page, which places every order with its POs already approved, or sends it back with a required reason. A sent-back cart can be revised and resubmitted. The cart page's tabs (Cart, Waiting on approval, Ordered, Sent back) keep every cart visible, and a co-op listing that links out can't be added.

Each **order** now runs to reconciled, with a timeline on its page. A P-card order goes placed → shipped → received → charge matched to the receipt. A PO order goes waiting on approval → approved → shipped → received → invoice matched (PO, receipt and invoice agree) → payment approved and the PO closed. Every step records what happened and when, and every order carries a demo GL code for its department. **Procurement → Orders** is the agency-wide table, filterable by person, department, status and payment, with each order's progress, its next step as a button and a CSV export for reconciliation. Riverbend is seeded with four earlier orders at different stages.

**Verification.** Supplier badges now open the checks behind them: SAM.gov registration, the SAM.gov exclusions list, Section 889, certificate of insurance, performance bond and each certification. Every check shows its source and the date it was last run, and expiring or failed checks show as "N checks to review." Storefronts list the checks in full. Only the eight fictional demo suppliers carry results, all labeled as demo data. Real companies (Tyler, Dell and the rest) show every check as not checked yet, because Loci holds no real SAM.gov or insurance results for them.

## Look and feel: USWDS, with retail presentation

Loci is built on the [U.S. Web Design System](https://designsystem.digital.gov/) (USWDS), and USWDS sets its colors, type and components. Editorial home-goods retail, in the spirit of Crate & Barrel, shapes only how products are presented. No retailer's name, logo, fonts or photography are used.

- **From USWDS:** USWDS's default theme, generated from the official `@uswds/uswds` package by `node scripts/uswds-theme.mjs`. That means primary blue-60v (#005ea2) for actions, with primary-dark hover and primary-darker press. It also covers cool-gray neutrals, the success, warning, error and info families, Source Sans for body and UI, bold Merriweather headings, 4px buttons, 2px outline buttons, 2px card borders with 8px corners, square text inputs, and the 0.25rem focus-blue outline. Components follow their USWDS counterparts: the basic header with a 4px current-page bar, buttons, tags, slim alerts, a summary box, checkboxes, a segmented button group, a modal, and a step indicator with a process list. USWDS token names work as classes (`bg-primary`, `text-base-dark`, `border-base-lighter`).
- **From retail:** result tiles laid out like a product grid (a large image panel, a small spaced maker name, the product name, then price and actions), generous whitespace, hairline rules between results sections and a single search field with plain underlined example searches.
- **The logo** is an app-style mark: a geometric "A" on a rounded blue tile, next to "Loci" in plain bold type (`components/Logo.tsx`).

`AGORA_THEME` in the script holds Loci's changes to USWDS's defaults, the equivalent of a project's `_uswds-theme.scss`; today it only sets the corner sizes. The script writes the tokens to `lib/uswds-theme.json` and the light and dark CSS variables to `app/theme.css`, which `tailwind.config.ts` reads. Loci isn't a federal site, so it doesn't use the USWDS government banner ("An official website of the United States government") or the identifier.

## Product decisions

These are settled, and the app follows them:

- **The free-plan limit counts RFP Lite only.** Handing a request to Sovra's RFP tool or to the agency's own tool (Euna, OpenGov, Bonfire) never counts toward the five free RFPs a year.
- **Only suppliers can buy placement.** Co-ops can't pay to rank higher, which keeps them neutral, since competing vendors sell through the same co-ops.
- **Resellers stay in results, last.** Reseller contracts appear under "Other ways," after the agency's own, state and co-op routes. Civic Marketplace-type channels aren't included.
- **The demo member lists stay, labeled.** WSPC's list, and the two fictional cities added to Sourcewell's, are marked as demo data. Real agencies are matched against the published rosters in the co-op directory, and lists a co-op shares are uploaded through **Co-op member lists**.

## Supplier plans, placements and listing fees

Suppliers earn Sovra money in four ways, all in the existing ledger options:

- **Claiming a storefront.** A storefront that Loci built from public contracts has a **Claim this storefront** link. A work email on the company's own website domain verifies the claim at once. Any other email waits for Sovra review: an admin sees an **Approve claim** button on the storefront, and the claim waits under **Supplier claims** at `/admin`, which can also reject it. Once claimed, the supplier views act as that company. A **Viewing as** picker switches between the storefronts the account may run: the fictional suppliers' demo storefronts, and any it claimed itself (an admin may run any).
- **Storefront plans** (option 6): Basic is free. Profile ($500/yr) adds the supplier's own tagline and description and targeted placements. Profile with catalog ($1,500/yr) adds a published catalog and featured product lines. An upgrade bills only the difference for the year.
- **Targeted placements** (option 5): a supplier picks a category and a state, or anywhere. Its listings show as Sponsored only on searches in that category, for agencies in that state. Billing is still $2.00 per results page shown. Sponsorship can move a listing up within its own kind of contract; it never changes a fit score or which contracts an agency can use. Placements need a claimed storefront and either a paid plan or Edge Win and up. In the seed, National Furniture's sponsorship is a placement for furniture, anywhere.
- **Listing fees** (option 2): a supplier with no contract at all (small purchases only, like MetroMart) pays $150 a year to appear. Its listings are hidden while the fee has lapsed.

Manage all of this under **Supplier → Plans and placements** (`components/SupplierPlans.tsx`). The rules are in `lib/suppliers.ts`.

## Verified suppliers only

Results have a **Verified suppliers only** checkbox. A supplier counts as verified when its checks have been run and every one passed; an expiring certification counts as not passed. A performance bond isn't required, since most purchases don't need one. The filter applies to both product tiles and co-op contracts, and a line says how many options it hid, with a link to show everything.

## Dark mode

The account menu has **Appearance: System, Light, Dark**. System follows the computer's setting. A saved choice is applied before the page paints, so there's no flash of the wrong theme.

USWDS doesn't define a dark theme, so `scripts/uswds-theme.mjs` builds one. It mirrors each color's grade within its own USWDS family: light surfaces become dark ones, ink becomes light, and borders, status colors and route colors move to the grade that reads on dark. Every dark value is still a USWDS system color. White and black swap too, so text on a filled button stays readable. The script writes every color as a CSS variable with light and dark values (`app/theme.css`), and Tailwind reads the variables. Category tiles mix their hue into the page surface, so they're pastel on white and deep on dark. Avatars, storefront banners, the announcement strip and modal backdrops keep fixed colors in both modes.

## Vendor price catalog

Loci also carries Tyler Technologies' March 2025 price catalog (`seed/catalogs/tyler-technologies-price-catalog-2025-03.xlsx`), so buyers can ask for software and services such as "jury management", "open data portal" or "an implementation consultant". `npm run import:catalog` turns the spreadsheet into `seed/catalogs/tyler-technologies-2025-03.json`, which the seed loads on every reset.

The catalog keeps each price inside the product description, so the importer reads only the price line and lists a row only when it holds one clear price. Of 1,672 rows, 1,350 import cleanly; the other 322 are skipped with a reason recorded in the JSON (no price, a price range or "up to" ceiling, tiers or a minimum spread over several lines, or a price with a percentage or second component). Products priced in tiers (by population or volume) show as one product with a tier picker, preset to the tier that fits the buyer's population. Loci carries the 100 Tyler products a city, county or school district is most likely to buy (204 price rows across their tiers). `scripts/feature-tyler.mjs` picks them: core subscriptions and platforms score up; third-party add-ons, training and implementation hours, hardware, usage fees, and state-, federal- or enterprise-scale offerings score down; and each product line has a quota so payments, permitting, records, public safety, open data and the rest are all represented. The other rows stay in the JSON, so widening the cut means changing the quotas and running `npm run import:catalog`.

The catalog names rows the way its price sheet does ("Flip to Saas: Tax Pro (Tier D -population >280,000)", "Task - Custom"), so `scripts/name-tyler.mjs` gives each featured product a plain name and one-line description ("Property assessment and tax software, cloud"), turns tier codes into readable sizes ("Population 80,001–160,000", "1–50 sworn officers"), and hides six rows that duplicate another tier or serve only federal buyers. The catalog's own wording stays searchable, and the product page shows where each item sits in Tyler's catalog. A product added to the featured set without a name stops the import with a list of what's missing.

It is New Jersey's state contract on NJSTART, 26-TELE-114629, so it is open to New Jersey public entities only. Tyler has no seeded reviews or ratings.

The live site runs on **Railway**, which redeploys every push to `main` (`riverbend-storefront-production.up.railway.app`). Render also works, using the `render.yaml` blueprint in this repo. ## Contract parsing

There are two sets of contract files. The **samples** in `seed/contracts/` are the one-click cards on the upload screen; nothing is imported until someone picks one, so the demo always shows a live parse. The **test files** in `public/test-contracts/` are for trying a real upload: download one from the upload screen (or grab it from the repo) and drag it into the drop zone.

| Test file | What it exercises |
| --- | --- |
| `techsource-it-peripherals.docx` | A Word table, a reseller source, and a SKU already in Loci at a new price |
| `evergreen-public-works-materials.pdf` | No piggyback clause, so other cities' marketplaces stay locked; a price range lands in Unresolved |
| `fleet-parts-price-list.csv` | A bare price list with no contract terms; type a supplier name before publishing |
| `scanned-custodial-contract.pdf` | An image-only scan, which shows the no-OCR message |

`npm run seed:contracts` regenerates both sets.

Uploads are stored under `uploads/` keyed by file hash, and parse results are cached per hash, so re-opening is instant. Reading a contract can take most of a minute, so the upload route answers at once with a job id and the page asks for the result until it is ready (`lib/parse-jobs.ts`); a slow read is never one long request. A read that is never published is dropped after a day. The parser never invents a price. Ranges, "contact for quote", TBD and "per attached schedule" all land in **Unresolved** with the source text quoted. When Claude does the structuring, every price it returns is checked against the document text, and any price that can't be found there is moved to Unresolved. Scanned PDFs and contracts over 60 pages get a clear message rather than a silent failure.

## Deliberate deviations from the spec

- **Folding tables cost about $260, not $64.** At $64, 40 tables come to $2,560, which wouldn't trigger the PO and approval steps the demo script calls for. Riverside is $264 and the state contract is $259, so 40 tables just clear $10K.
- **National Furniture Co. is on Edge Win, not Discover.** The spec allows sponsored placement only for Win and Position, but the demo script needs National's listing to be sponsored.
- **Option 2 also fires on a contract's first order** if the contract predates the city's marketplace. This is how step 3's "options 3 and 2 (if first time)" is realized.
- **Co-op and reseller orders carry listing fees only**, with no transaction fee (the default from open question 12.1). This is noted in the ledger.
